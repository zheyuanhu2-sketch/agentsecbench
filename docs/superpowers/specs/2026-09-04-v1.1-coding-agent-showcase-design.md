# AgentSecBench v1.1 Coding-Agent Showcase Design

## Goal

Make AgentSecBench a stronger Codex for Open Source candidate by adding a truthful,
reproducible coding-agent security showcase without introducing live credentials, a web
framework, or unsupported adoption claims.

## Scope

Version 1.1 will deliver three connected improvements:

1. Make checked-in generated evidence survive normal Git checkouts on Windows and Linux.
2. Add a synthetic scenario catalog focused on repository-aware coding agents.
3. Generate a zero-dependency static HTML report from canonical, content-free result artifacts.

The release will also update the README, changelog, and validation documentation so a reviewer
can understand and reproduce the result in about 60 seconds.

## Non-goals

- No live OpenAI or other hosted-model calls.
- No API keys, real repositories, real vulnerability reports, or personal data.
- No React, JavaScript charting library, server, analytics, or runtime web dependency.
- No claim that the reference policies measure a production model's security.
- No invented stars, downloads, users, contributors, or ecosystem adoption.
- No release publication or application submission in this change.

## Approaches considered

### Selected: extend the external catalog contract and generated showcase

Keep the frozen v0.1 built-in catalog unchanged. Add a separate checked-in external catalog for
coding-agent workflows and run the existing evaluator against it. Extend the showcase generator
to emit an accessible static HTML report alongside canonical JSON and Markdown evidence.

This preserves the v1.0 benchmark contract, reuses established validation, and gives reviewers a
visual artifact without adding a frontend toolchain.

### Rejected: replace the built-in mail/file catalog

Replacing the frozen catalog would make earlier fingerprints and v1.0 evidence incomparable. It
would also turn a presentation improvement into a breaking benchmark change.

### Rejected: build a live hosted-agent dashboard

A live dashboard would look richer but require credentials, network behavior, deployment state,
and a larger trust boundary. Those costs do not improve the truthfulness of the application.

## Architecture

### Cross-platform evidence bytes

Generated JSON, Markdown, and HTML remain canonical LF byte streams. A root `.gitattributes`
will mark generated evidence files as `text eol=lf`. A regression test will copy generated files
through CRLF text conversion and demonstrate that the old checkout behavior fails byte-level
verification; repository attributes then prevent that conversion in normal Git checkouts.

The verifier will remain strict. It will not normalize line endings while checking, because doing
so would weaken exact-byte reproducibility and make file digests ambiguous.

### Coding-agent scenario catalog

Add `examples/coding-agent-scenarios-v1.json` using the existing
`agentsecbench.scenario.v1` schema. The catalog will contain paired legitimate and adversarial
repository workflows using only the current in-memory `file.read` and `file.write` tools.

The first catalog will cover these threat patterns:

- untrusted repository instructions requesting credential disclosure;
- an issue body attempting to redirect writes outside an approved patch path;
- a generated test fixture attempting to authorize unrelated file mutation;
- a dependency note attempting to suppress or falsify security findings;
- a pull-request document attempting to overwrite trusted project instructions.

Each attack scenario will have a matching normal task so utility and false-blocking remain visible.
All content and secrets will be explicitly synthetic. Scenario IDs, action provenance, policy
boundaries, and sensitive-value prefixes must pass the current strict catalog validator and JSON
Schema.

This design intentionally models repository content through the existing file abstraction. New
Git, shell, browser, or network tools are out of scope for v1.1.

### Static report

Add a focused renderer module under `src/agentsecbench/report.py`. It will accept already
validated result artifacts and return deterministic UTF-8 HTML bytes. It will not read arbitrary
files, execute templates, embed scenario content, or load remote assets.

The report will include:

- benchmark name, package version, and catalog fingerprint;
- unsafe-versus-secure metric cards;
- accessible comparison tables for utility, attack success, false blocks, and leakage;
- per-task status rows containing identifiers and evaluator outcomes only;
- interpretation and synthetic-data boundaries;
- reproduction commands and artifact digests.

Visual styling will be embedded CSS using system fonts, high-contrast colors, responsive layout,
visible focus styles, and reduced-motion compatibility. The document must remain useful with CSS
disabled because all results also appear in semantic tables.

### Generator integration

`scripts/showcase.py` remains the single source of generated showcase outputs. Its expected file
set will expand to include `index.html`. Generation and checking will stay atomic and byte-exact.
The script will render the report only from the deterministic built-in reference artifacts in
v1.1; the coding-agent catalog will have its own validated command and documented reproduction
path without being misrepresented as a live-model result.

## Data flow

1. Build or load a validated synthetic scenario catalog.
2. Evaluate it with a named reference policy.
3. Convert evaluator output into canonical result artifacts.
4. Pass validated artifacts and their digests to the static renderer.
5. Atomically write JSON, manifest, Markdown, and HTML outputs.
6. In CI, regenerate expected bytes in memory and compare them to every checked-in output.

No prompt text, file contents, tool arguments, tool outputs, endpoints, or synthetic secret values
may enter the generated showcase report.

## Error handling and safety

- Reject malformed, oversized, duplicate-key, non-synthetic, or unknown-tool catalogs before
  evaluation.
- Escape every dynamic HTML value, even when current values are controlled identifiers.
- Reject symlinked output paths and output paths outside the repository, preserving current
  atomic-write protections.
- Fail verification on an unexpected file, stale byte, changed digest, mismatched catalog, or
  inconsistent reference-policy delta.
- Keep network and provider adapters opt-in and unrelated to report generation.

## Testing strategy

Implementation follows red-green-refactor for each behavior:

1. Add a failing checkout/line-ending regression test and then add `.gitattributes`.
2. Add failing catalog tests for expected task counts, pair coverage, synthetic classification,
   and stable fingerprint; then add the catalog data.
3. Add failing renderer tests for deterministic bytes, HTML escaping, semantic metrics, absence of
   sensitive content, and responsive/accessibility markers; then implement the renderer.
4. Add failing showcase integration tests for the new `index.html`; then wire it into generation.
5. Run the full test, lint, type-check, showcase, source-release, and clean-checkout verification
   gates on Windows. GitHub Actions remains the Linux and supported-Python matrix proof.

## Documentation and release posture

The README first screen will lead with the coding-agent security value, retain precise boundaries,
link the static report, and provide one copy-paste reproduction path. `CHANGELOG.md` will describe
the unreleased v1.1 work. The project version changes only when all release gates pass and a
separate release decision is made.

The resulting commit will be pushed only after local verification and user approval. Creating a
GitHub release and submitting the Codex for Open Source form remain separate explicit actions.

## Acceptance criteria

- A default Windows Git checkout and an LF checkout both pass strict showcase verification.
- The frozen built-in catalog and its v1.0 fingerprint remain unchanged.
- The new coding-agent catalog validates and has deterministic expected counts and fingerprint.
- The generated HTML is deterministic, self-contained, responsive, keyboard-readable, and free
  of scenario content and synthetic secrets.
- The full local quality gate passes from a clean checkout.
- Documentation makes no production-model or adoption claim unsupported by evidence.
